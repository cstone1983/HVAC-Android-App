## L1 — P0: a preset of 60 °F can never be applied, and silently suspends the zone

**Proven end to end during the live test.** This is the highest-value finding of the day.

The heads are Celsius devices. At 61 °F the raw register reads `set_tmp: "160"` — **16.0 °C**. The
hardware floor is 16.0 °C = **60.8 °F**. Home Assistant advertises `min_temp: 60` because it rounds
that conversion down, and `input_number.*_temp` helpers are configured `min: 60.0`. So the UI
permits a value the hardware refuses.

Measured boundary: **60 rejected, 60.5 rejected, 61 accepted.**

Observed chain, with nobody touching anything:

```
away preset = 60
  → climate.set_temperature 60 rejected by the head
  → head keeps its old setpoint (bedroom_1 stayed 68, basement stayed 65)
  → watchdog reads the difference as drift
  → override latches (both at 09:30:31, two ticks after the failed write)
  → zone suspended from automation until cleared by hand
```

Telegram reported the write failures correctly — `HVAC Apply error … set_temperature 60 … The
service was not able to process your request` — so detection works; nothing acts on it.

Currently configured at 60 and therefore permanently broken: `bedroom_1_away_temp`,
`basement_away_temp`, `basement_night_temp`, `bedroom_1_night_temp`.

**The fix already existed on the cooling side.** The disabled `HVAC - Master Sequencer` contains:

```jinja
{% if global_mode == 'cool' %}{{ [raw_target_temp, 64.5] | max }}{% else %}{{ raw_target_temp }}{% endif %}
```

18 °C = 64.4 °F, so someone hit this identical wall on cool and solved it with a floor — carried
forward into the current code as `COOL_FLOOR_F = 64.5`. It was never applied to heat.

### What the register data actually shows

Reading `set_tmp` against the reported °F on every head gives the real ladder — **0.5 °C steps
starting at 16.0 °C**, with HA showing a rounded °F view of it:

| head | HA shows | `set_tmp` | actual °C |
|---|---|---|---|
| bedroom | 68 | 200 | 20.0 |
| anthony | 70 | 210 | 21.0 |
| living / dining | 66 | 190 | 19.0 |
| bedroom_2 | 62 | 165 | 16.5 |
| basement / autumn | 61 | 160 | 16.0 |

The integration converts °F→°C, checks the result against the 16.0 °C floor, **then** rounds. That
explains 60.8 failing too: `(60.8−32)×5/9` is `15.999999999999998` in floating point, just under.

Ten days of recorder history confirm no head has **ever** held a register below `160`. The lowest
value any head has reached is exactly this floor, so the 60 preset has never once applied.

Fujitsu's own app labels the 16.0 °C rung "60"; Home Assistant labels it "61". Same physical
setpoint, two labels — nothing is lost by clamping.

### Fix applied and verified live (2026-09-21)

`HEAT_FLOOR = 61` added in all three places that compute a target, so they cannot disagree:

- `HvacModels.kt` — `HEAT_FLOOR_F = 61.0`, applied in `scheduledSetpoint`
- `HVAC Watchdog` → `Evaluate` — clamps `expected` before the drift comparison (published `de542c92`)
- `HVAC Controller` → `Compute Sequencer Actions` — clamps `targetTemp` before the write (published `9666380b`)

The helpers deliberately keep `min: 60`, so 60 stays selectable and simply resolves to the floor.

**Live proof, same house, same day:**

| | before the fix (09:28) | after the fix (12:09) |
|---|---|---|
| write | `set_temperature 60` rejected | `set_temperature 61` applied |
| head | kept stale 68 / 65 | holds 61 / 61 (`set_tmp 160`) |
| watchdog | latched override at 09:30:31, 2 ticks | 3 ticks elapsed, **no latch** |

All seven heads then held exactly their intended targets simultaneously — 66/61/62/61/66/70/61 —
which had not been true at any point earlier in the day.

### Still open on this thread

- `conf_turn_on_before_set_temp` is `false` on all seven `fujitsu_airstage` entries. Enabling it
  makes the integration power a head on before writing a setpoint, fixing part of the
  turn_on→mode→temp ordering problem at source — which matters more than usual while A1 keeps
  `awaitHeadState` down to a 1.5 s sleep. **Caveat:** it also means any setpoint write to an off
  head turns it on. The sequencer never does that, but the app's preset "apply now" stepper does

- Blocked from here: `ha_set_integration` is refused by the auto-mode classifier as

  added. Needs either that rule or a manual change in the HA UI.

## Confirmed defects — app

### A1 — P0: the WebSocket never connects on the deployed panels

`HvacViewModel.kt:842`:

```kotlin
val token = sharedPrefs.getString("ha_token", "") ?: (try { BuildConfig.HA_TOKEN } catch (e: Exception) { "" })
```

`getString` with a non-null default never returns null, so the elvis can never fire. The guard on
the next line then skips `connectWithFailover`. Compare `_haUrl` at `:373`, which correctly uses
`getString("ha_url", null) ?:` — so the URL resolves and only the token is empty.
`HomeAssistantClient.kt:99` *does* fall back to `BuildConfig.HA_TOKEN`, which is why REST works and
the app looks healthy.

Live corroboration: neither tablet has an `ha_token` key in `hvac_settings.xml`, none of the ten
`last_known_*` keys written inside `wsManager.states.collect` exist, and there are zero
`HA_WS_Manager` log lines against ~11,800 okhttp lines.

**Why this matters more than it looks:** `awaitHeadState` short-circuits to a **fixed 1.5 s sleep**
when the socket is down. So the bounded-wait ordering fix from `0c71c98`/`ae019a5` **is not in force
in production** — the panels are running the pre-fix fixed-sleep behaviour. Several things believed
fixed are not actually active on the wall.

### A2 — P0: two quick mode taps leave a head in one mode holding the other family's setpoint

`HvacViewModel.kt:1825-1881`. Each tap launches an independent `viewModelScope.launch`; there is no
per-entity mutex and no cancellation. Both read the same stale `current`, both race through
turn_on → set_hvac_mode → await → set_temperature, and **each computes its setpoint from its own
target mode**. Whichever wait expires last wins the setpoint — frequently the loser of the mode race.

The button has no debounce (`HomeStatus.kt:833-877`) and `_actionFeedback` claims success at `:1827`
*before* any call is made, so a user who taps again because "nothing happened" is behaving exactly as
the UI invites.

Reachable outcome: Autumn cooling toward 61, or heating toward 75.

### A3 — P0: `main_level` is a single head in the app

`layout_config.json:151` maps `main_level` to `climate.hp_living_room` only.
`climate.hp_dining_room` appears at line 126 solely as a room sensor. Meanwhile
`HvacModels.kt:375-382` correctly declares the zone as spanning outdoor units 1 **and** 2.

Three consequences:

1. **The conflict guard fails open for unit 2.** `findModeConflict` reads `main_level`'s mode from
   the living-room head. If the *dining* head is the one committed to a family, the zone reads
   `off` → NEUTRAL → no conflict, and a conflicting mode is sent to Anthony or Autumn.
2. **The card hides a split.** The 40-minute main-level split would have been invisible on the panel.
3. **Dining is rendered twice.** Confirmed in my own baseline screenshot: "Main Level 77°" and
   "DINING 76°" side by side — the exact defect `hideRoomSensorIds` exists to prevent, which lists
   `living_room` and `basement` but not `dining_room`.

### A4 — P1: `lastNonOffHvacMode` never learns `dry`, and is persisted before the write lands

`:1006-1011` syncs it for `heat` and `cool` only; `:1395-1400` writes it for `heat`, `cool` **and
`dry`**, and commits to SharedPreferences *before* the service call at `:1411`. Nothing reverts on
failure, and with the house `off` — its normal resting state — the corrective path never runs.

Consequences: the compressor-reversal confirmation fails open on a dry→heat change; the power button
brings a sleeping head up in the wrong family; the three panels can disagree with each other
indefinitely; and the confirm dialog renders the stale value as the *current* mode
(`HvacDashboard.kt:842`) while the same screen shows OFF highlighted.

### A5 — P1: the setpoint is written for the mode that was *requested*, not the one reached

`:1861-1874` calls `awaitHeadState(...) { it == target }` and **discards the Boolean**, then writes
the setpoint regardless. The ceiling is 8000 ms while the Airstage integration reports on a ~10 s
round robin (measured ages across seven heads at one instant: 1.3/7.1/2.3/2.2/8.8/0.4/3.4 s), so the
wait expires routinely even when everything is working. n8n uses 15 s for the same reason.

Result: a head still running cool can receive the heat setpoint.

### A6 — P1: a failed `turn_on` is swallowed

`:1836-1843` does not assign `performServiceCall`'s `Boolean` result, and discards the following
`awaitHeadState { it != "off" }` too. Contrast `:1845-1852`, where `set_hvac_mode`'s result *is*
checked. `HomeAssistantApi.callService` returns `Response<ResponseBody>`, so a non-2xx does not
throw. The head stays off, `set_hvac_mode` lands on a sleeping unit and is ignored, and the banner
says the zone is heating — the exact failure `0c71c98` was written to fix.

### A7 — P1: the "apply now" preset stepper pushes the wrong family's number

`HvacDashboard.kt:3285-3302`. `activeModeForPresets` comes from the **house** mode, never the zone's.
The popup detects the divergence 30 lines earlier and renders "This zone is set to COOL while the
house is HEAT", then ignores it when choosing the block. Tapping `+` on the ACTIVE row sends a heat
setpoint straight at a cooling head.

### A8 — P1: the car is a second, older copy of the command logic

`CarHaRepositoryHelper.kt:285-341`. It never sends the scheduled setpoint (`grep` for
`set_temperature` in `com/example/car/` returns nothing), uses a fixed `delay(1200)` instead of a
bounded wait, and implements only the *same-condenser* half of the conflict rule — omitting the
house-mode tier that `HvacModels.kt:442-449` treats as outranking everything. So the car can send a
mode the panel would refuse, and reports success either way.

### A9 — P1: HA token and GitHub PAT are written to logcat

`HomeAssistantClient.kt:36` sets `HttpLoggingInterceptor.Level.BODY` unconditionally — not gated on
`BuildConfig.DEBUG` — with `Authorization: Bearer <token>` added at `:27-31`. `GithubClient.kt:60`
uses `Level.HEADERS`, which also logs the PAT. Installed builds are debuggable. This undoes the PAT
masking fix on the settings screen. It also floods the log buffer: ~11,800 okhttp lines filled the
entire main buffer in under six minutes, so nothing else survives long enough to be read.

### A10 — P1: a rejected token produces an unbounded reconnect loop

`HomeAssistantWebSocketManager.kt:367-372` → `301-308` → `650-681`. On `auth_invalid` it sets
`canRetry = false`, but `onClosed` does not special-case it and calls `scheduleReconnect` anyway.
`canRetry` is written twice and **read nowhere**. Roughly 8,600 failed logins per panel per day, and
because `consecutiveHostFailures` increments on each, it also flaps primary↔backup every two
attempts. The panel shows a generic "Network error", never "your token is bad".

### A11 — P1: there is no APK OTA path at all

`checkForUpdates` (`:2047-2171`) sets `pendingAssetUrl` to the `layout_config.json` raw URL in
**both** branches, so `isApk` is always false and the install code is unreachable.
`isNewerVersion`, `getLatestRelease` and `getReleases` have no call sites. The release notes CI
generates tell the user to install over the air, which is not possible.

Separately, **the CI signature mismatch is confirmed by construction**: `android-release.yml:41`
runs `assembleDebug` on ephemeral runners, the debug build type has no `signingConfig`, and
`~/.android` is not cached — so every CI run mints a fresh key. Not only can a CI APK not install
over the current build, **two consecutive CI builds cannot upgrade each other**. CI also overwrites
`.env` with `.env.example`, whose token is the literal `YOUR_HOME_ASSISTANT_TOKEN`.

### A12 — P1: the alert strip pushes the bottom zone row off screen on the Tab A9

`HvacDashboard.kt:1034-1036` budgets `rowSpacing * zoneRowCount`, but the section emits
`2 + zoneRowCount` items — so there are `zoneRowCount + 1` gaps — and subtracts nothing for the
`HomeAlertStrip` itself (~42 dp when visible). Measured slack on SM-X110 is ~6 dp. Any open garage
door, offline state or command failure clips the bottom row's "SET nn° / OFF" line. The Tab A8 is
unaffected (hits the 190 dp clamp with ~72 dp spare). `de4dc60` fixed the control-card estimate, not
this.

### A13 — P2: a stale open-door alert outranks the offline banner

`HomeStatus.kt:177-194` orders alerts `openDoors → isOffline → feedback`. `openDoors` is computed
from the last-known state map. So when the panel is disconnected it keeps asserting "GARAGE SOUTH
OPEN" in red from cached data, and that assertion suppresses the very banner that would say the data
is stale — and also swallows command-failure messages.

### A14 — P2: pool diagnostics and status pills still fabricate readings

The hero metrics were genuinely fixed, but `PoolDashboardView.kt:1250` `battery ?: 4536.0` renders a
green "IDEAL" verdict on an invented number, `:1256-1257` invent hardware serials, `:291`
`waterStatus ?: "Balanced"` reads BALANCED for a missing sensor, and `:299` invents "1 ACTIONS REQ".
Compounding it, `HvacViewModel.kt:1178-1192` makes every pool field sticky — an `unavailable` sensor
silently retains its last value forever, rendered identically to live.

### A15 — P2: presence popup reports history it never read

`HvacViewModel.kt:1660-1665` returns `emptyMap()` on any exception, which `HomeStatus.kt:351-361`
cannot distinguish from a real empty result — so every person renders "No change in recorded
history" and "30d+" when the recorder query simply failed.

### A16 — P2: other confirmed-but-minor app items

- OTA history can never show ACTIVE: `HvacDashboard.kt:4381` compares against `BuildConfig.VERSION_NAME` ("v13.0") instead of `layout_commit_sha`.
- The "Simulated Update Version" control is inert but toasts "OTA update is now available."
- Reset toast hardcodes "Default v5.1.0!"; the bundled layout is 6.2.0.
- Light popup shows "BRIGHTNESS 100% — 255/255" for a light with no `brightness` attribute.
- Solar shows two different numbers for today's generation (integrated resample vs the daily meters), and reads "NET EXPORTING 0 W — producing excess clean power" when both sensors are missing.
- Vane fallback list `["Auto","Swing","1".."5"]` contains **no** valid option (live options are `Highest/High/Low/Lowest/Vertical Swing`); the fan fallback is valid but omits `Medium`.
- Every push to `main` raises an update banner, because the check compares the branch head rather than whether `layout_config.json` changed.

## Confirmed defects — n8n

### N1 — P0: the echo gate is blind for the first 3–17 s after every write

`Start Confirm Window` computes `sent_at`, but the only node that writes `last_write_at` into the
data table is `Release Lock After Write`, which runs *after* the confirm window and the minimum-gap
hold. The earlier fix moved the **value** to send time; it did not move **when the row changes**.

Proven: Apply execution `7157` had `sent_at = 11:02:16.780` but wrote the row at `11:02:20.019`.
Controller `7167` — the echo of that very write — checked the gate at ~11:02:17.55 and **missed**;
Controller `7168` checked 7 ms after the release and matched. The gate opened 2.5 s too late and
caught the wrong event.

The window is `last_write_at > now − 15000`, but the row only appears at `sent_at + confirm + gap`.
If the write is never confirmed the row appears at +17 s — after the window has already closed — so
**the gate provides zero protection exactly when the head is slow**, which is when divergence is
most likely. Same failure mode as the 2026-09-20 main-level split.

`AUDIT-2026-09-20.md` records this as fixed. The write-side half is; the timing half is not. That
status line is wrong.

### N2 — P0: `sent_at` is stamped when the HA call *returns*

The node's own comment claims it runs "immediately after Send Command To HA" — which is true of
completion, not of issue. In `7157` that node took 6094 ms, and HA's resulting `last_changed` was
`11:02:15.032`, **1.75 s before** `sent_at`. The nominal 15 s window starts up to 6 s late and can
begin after the echo has already been forwarded.

### N3 — P0: the run mutex is released ~11 s before the writes it guards land

All eight `Dispatch Zone - *` nodes carry `waitForSubWorkflow: false` in the published Controller.
Verified node-by-node, and in execution timings:

| Time | Event |
|---|---|
| 11:02:05.310 | Controller 7150 acquires run mutex |
| 11:02:09.570 | Controller 7150 **releases** it |
| 11:02:10.723 | Controller 7158 **acquires** it — 1.15 s later |
| 11:02:16.780 | Apply 7157 finally sends 7150's `set_hvac_mode off` |

Two runs computed against overlapping state while a third's writes were in flight. Corroborating:
`Renew Run Mutex` filters on `owner eq mutex_token`, and in execution `7163` it matched **no row**,
because the owner had already been blanked — the renewal mechanism is inert on every run.

Ordering is guaranteed *within* a Zone Runner but not *across* two racing ones.

**Do not fix this alone:** `Try Acquire Run Mutex` sets a 150 s TTL, while a full seven-head sweep
under `waitForSubWorkflow: true` is ~350 s. Flipping the flag without raising the TTL (or confirming
`Renew Run Mutex` starts firing) would strand the mutex mid-sweep. They ship together.

### N4 — P0: the watchdog latches an override on a zone it turned off itself

Section C turns off every head in a conflicted zone, but the watchdog's own writes never stamp
`last_write_at` — its `Get Write Lock` node is a read-only `get`. Next tick, `familyOf('off')` is
`neutral`, the conflict clears, and section A sees `'off' !== 'heat'` → drift → override latches,
with a Telegram blaming a human: *"… was turned off while the house is set to HEAT"*.

### N5 — P1: a future-dated timestamp disables the whole watchdog silently

```js
const recentWrite = !isNaN(lastWriteAt) && (now - lastWriteAt) <= RECENT_WRITE_MS;
```

A future timestamp makes the difference negative, which satisfies `<= 30000` — so `recentWrite` is
true forever. `lockHeld` behaves the same way for a far-future `expires_at`. Both set `skipReason`,
both are treated as transient, so sections A, C and D are skipped with no Telegram and no error.
Both values are a `MAX` across all nine rows, so one bad row poisons every head. Clock skew or a
seconds/milliseconds slip is enough. Nothing would ever reveal it — which matches the previously
observed long silent stretch.

### N6 — P1: `last_fan_write_at` is written but never read

The write side is correct and channel-aware. The read side was never split: `Check Recent
Self-Write` is the only reader and filters solely on `last_write_at`. Consequences, both observed:
a fan/vane write's own echo is **no longer suppressed** (execution `6239`, arriving 2.07 s after the
stamp, missed the gate and contended for the mutex across three attempts) — a regression introduced
by the split — and fan/tilt events are gated by the wrong channel, so a genuine human vane change
within 15 s of any mode write is silently discarded (execution `7166`).

### N7 — P1: an unconfirmed write is reported to the Zone Runner as success

`Confirmed Or Timed Out?` branches on `done = ok || expired`, so both paths reach the release and
Apply returns normally. `Apply Action (ordered)` has `onError: continueRegularOutput`, so the
sequence continues. A `turn_on` that the head never acknowledges is followed by `set_hvac_mode` and
`set_temperature` to a sleeping unit, and `last_write_at` is stamped regardless — so the echo gate
then treats the head as recently written.

### N8 — P1: the Controller's own override-clear writes re-trigger the Controller

`Check Recent Self-Write` maps any non-`climate.hp_` entity to lock_key `'__none__'`, and **no row
with that key exists** — so a helper event can never be gated. `clearOverride()` writes
`input_boolean.override_<zone>`, and the forwarder triggers on all six with no `for:` debounce.
Observed: one schedule change produced 2 Controller runs, 5 Zone Runner runs, 6 Apply runs and ~7 s
of lock contention to perform 4 actions.

### N9 — P1: conflict and split holds can be reset by a write to a *different* head

`lastWriteAt` is the maximum across all nine lock rows, not the row for the head being timed. Any
write landing 30–60 s before each tick resets the timer, so a genuine conflict on an untouched head
can never reach `CONFLICT_HOLD_MS` during a multi-zone sweep.

### N10 — P1: head-unavailable alerts are the one class not coalesced

Section B pushes a separate Telegram per head, outside the coalescing A/C/D use. An AP reboot sends
seven messages in the same second against Telegram's ~1/sec guidance, and `Send Telegram` has no
`onError` and no retry, so a 429 loses the alert.

### N11 — P1: the Bot can drive the house into a conflict and report success

`case 'm'` writes `global_hvac_mode` with no conflict pre-check. `Check Verify` then does
`if (!enabled || ovr) continue; total++;`, removing the offending zone from **both** numerator and
denominator — so it reports "✅ heat confirmed on 5 of 5 zones" while a held zone stays on the
opposing family, and the watchdog shuts that equipment down 45–120 s later.

### N12 — P2: other confirmed n8n items

- The `main_level` mirror in `Compute Sequencer Actions` copies mode across **outdoor units** without checking the destination unit's other heads, and runs *before* `zone_enable` and `override` are read — so a disabled or overridden main level is still written.
- The mirror's temperature guard compares the **raw** value but writes the **floored** one, so below the cool floor it fires forever without converging.
- `Notify Webhook` returns 200 before checking the token and the false branch is unconnected — rotate the secret and every alert stops with no symptom anywhere.
- Three guards use `$getWorkflowStaticData('global')` under proven concurrency; a lost entry is plausible but I could not demonstrate it.
- `Notify Mutex Timeout` says 200 s; the code sets 600 s.
- `Valid Event?`'s false branch is unconnected — a malformed entity id is dropped silently.
- The `:31` watchdog signature is n8n's incidental per-workflow spread, not configured. It is stable today but will move on re-activation or restart. `N8N-EDITING.md` presents it as reliable evidence; pin it or stop relying on it.

## Verified clean — checked specifically, no defect found

- **Fan/swing casing contract, end to end.** Heads accept `["Quiet","low","medium","high","auto"]` and `["Vertical Swing","Highest","High","Low","Lowest"]`. The asymmetric rule — `Quiet` keeps its capital, everything else lowercased, swing passed through unmodified — is correct in both directions and guarded by membership checks. Verified against live head attributes.
- **Lock atomicity.** `Try Acquire Lock` is a single data-table update with `lock_key = ? AND expires_at < now` — a genuine compare-and-swap. Proven under real contention (7163 failed three acquires while 7157 held the row, succeeded only after release).
- **Expression scoping — all 41 references** in Apply and the Controller resolve to the intended node, and every referenced name exists exactly as spelled. The previously-broken `Hold Minimum Gap` now reads `$('Init Action')` and is immune to node insertion. This bug class is not present.
- **Ordering within a Zone Runner** is strict (`mode: each` + `waitForSubWorkflow: true`), confirmed empirically.
- **Stranded locks.** All lock-holding nodes are TTL-bounded (90 s / 150 s); all error branches that matter route to a release; all ten rows currently read `owner: ""`. Zero error/crashed/running executions across all three workflows.
- **No legacy HA writer is live.** All nine `gemini_hvac_*` / `hvac_engine_*` automations are off. Only the two n8n forwarders are enabled.
- **Every option string every writer can send is a member of the live helper list** (except the app's unreachable fallback arrays), and the Bot re-validates numeric ranges from the helper's own attributes.
- **The Bot never writes `climate.*` directly** — only helpers — so it cannot latch an override, and its writes correctly are *not* treated as echoes.
- **Setpoint selection agrees three ways** across watchdog, Controller and Bot, including `dry` reading the heat helper.
- **Message-id handling, reconnect-storm guards and reconnect state merge** in the WS manager are individually sound (though unexercised in production, per A1).
- **FileProvider and install-intent plumbing** is correct — it is simply unreachable (A11).
- **Backup/extraction rules** correctly exclude `hvac_settings.xml`.

## Corrected and refuted

- **My own first call during the live test was wrong.** I saw the panel flip to "AT TARGET" and claimed it was asserting a state the heads had not reached.
