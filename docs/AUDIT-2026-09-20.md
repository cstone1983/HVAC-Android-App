## P0 — Can turn off heat that is running correctly

### P0-1. The Watchdog treats seven heads on two outdoor units as one thermal family

`HVAC Watchdog` → `Evaluate`, section C. **This is code I added at 14:29 today**, four hours
after the incident it was meant to catch, so it has had very little exposure.

`ALL_HEADS` is one flat array and `houseFamily` is one scalar. Unit 1 (living room, bedroom,
bedroom 2, basement) and Unit 2 (dining, Anthony, Autumn) are independent compressors. Heat on
one while the other cools is physically legal, and section C issues `climate.turn_off` against
every head that disagrees with its single house family.

January night, Anthony's room is cooling on Unit 2. Section C decides the house is cooling and
turns off three bedrooms and the basement on Unit 1, which were never in conflict with anything.
The Telegram message reads like a correction, not like "your heat is now off".

Compounding it: when `global_hvac_mode` is `off` the code does not conclude "no opinion". It
adopts the family of `LEAD_HEAD`, which is the living room, on Unit 1 — and lets that dictate
what Unit 2 heads may do. **Global mode is `off` right now**, and it is what both the
notification OFF button and the panel OFF button produce.

### P0-2. Drift detection punishes exactly the state that is supposed to allow manual control

`Evaluate`, section A. Drift is `s.state !== globalMode`. With `globalMode === 'off'`, **any**
running head is drifting, so after 55 seconds the Watchdog latches `input_boolean.override_<zone>`.

`off` means scheduling paused, manual per-zone allowed. So the one state that permits manual
control is the one that reliably punishes it. And `Compute Sequencer Actions` clears an override
only on a schedule change or a matching `zone_enable` toggle — **not** on a global mode change.
So when you switch the house back to heat, the room somebody warmed by hand is the single room
that gets no heat.

This is live. `override_main_level` latched twice today, at 11:55:31 and 12:31:31, both at
`:31` past the minute, which is the Watchdog's tick signature.

### P0-3. Turning off one main-level head drags the other off with it

The mirror in `Compute Sequencer Actions` is unconditional and has no guard against propagating
`off`. Watchdog turns off dining → forwarder fires → mirror sets living room to `off` too. One
spurious conflict verdict shuts down the whole main level.

### Status: fix written, **not applied** — needs you

The corrected `Evaluate` code is in the file I sent alongside this. The n8n write was blocked by
the permission classifier, so it has to be pasted into the node by hand. It:

- splits the heads into `unit1` / `unit2` and evaluates each independently, each led by its own
  main-level head;
- turns off every head in a zone explicitly rather than letting the mirror do it as a side effect;
- restarts the conflict timer if a write landed after the timer started, which closes the
  leading-edge window where an event has been forwarded but nothing has taken a lock yet;
- skips drift entirely when global mode is `off`;
- adds a section D that reports a main-level split — the 40-minute bug — and deliberately
  switches nothing off, because the two heads sit on different units and section C cannot see
  a split between them.

## P0 — Fixed and pushed (commit `ef14eba`)

### P0-4. The panel's conflict guard refused the one correction that mattered

`detectModeConflict` only returned a conflict when the global mode *disagreed*. When it agreed,
control fell through to the zone scan, and any other running zone in the other family became a
blocker. House on heat, one stray head on cool, you tap HEAT on main level — the correct fix —
and it was refused, naming the stray head. Once the house and a zone disagreed there was no path
back from the panel.

The offered override was worse: it wrote the global mode helper with the option already selected.
`select_option` with the current option is not a state change, so the sequencer never ran. Both
buttons in the dialog did nothing and the request was lost.

It also never applied the mode to the zone you tapped. The button said "switch everything to
heat", but a zone that was off stayed off, because the sequencer follows running zones.

### P0-5. Android Auto could send HEAT to a head in one tap, from a blank screen

The car screens render from `wsManager.states`, which is empty whenever the app is on REST
fallback. An absent entity was displayed as `OFF`, and the cycle maps `off → heat`. One tap on a
disconnected car screen sent HEAT to a head regardless of what it was actually doing, with no
conflict check, while driving. The guard added yesterday exists only in the touch UI.

Now: the mode is re-read live, an unknown state refuses instead of cycling, and a same-unit
conflict is refused with the reason. No override path in the car on purpose.

### P0-6. The car's schedule button has never worked and reported success every time

It sent lowercase `day`/`night`/`away` to a helper whose options are `Day`/`Night`/`Away`.
`select_option` matches exactly, so every call was rejected — and the return value was discarded,
so the driver was toasted "Schedule set to Night" each time. This also removed the car as a way
to clear a latched override.

### P0-7. The car's indoor average used two entities that do not exist

`climate.hp_bedroom_1` and `climate.hp_master_bedroom` both 404. Anthony and Autumn were omitted
entirely. Four real rooms, two phantoms, two omissions.

## P1 — The actual cause of the 40-minute split

### P1-1. The self-write echo gate is entity-scoped, and stamped at the wrong moment

`HVAC Controller` → `Check Recent Self-Write`. Two defects that compound:

**It keys on entity and time, never on what was written.** There is one `last_write_at` per head,
shared by the mode channel and the fan/tilt channel. Fujitsu heads reset swing and fan when the
mode changes, so the fan/tilt forwarder fires after *every* mode change and n8n writes the vane
back — stamping the same row the mode gate reads. Every mode change therefore opens a ~15 second
window in which a genuine mode divergence on that head is invisible.

**`last_write_at` is stamped at lock release**, after the 15s confirm window and after
`Hold Minimum Gap`. But HA has already changed state and the forwarder's 2s dwell has already
elapsed while Apply is still polling. So the gate also misses its own echoes, which is what
produced the mirror ping-pong that created the split in the first place.

Hard evidence: lock row `entity:climate.hp_dining_room` carries `echo_probe = 12:30:46.054`, and
`echo_probe` is written *only* when the gate matches. The state changed at 12:30:43.048, the
forwarder's 2s dwell put the POST at ~12:30:46. The masking write was a `climate.set_swing_mode`
on the same head from the fan/tilt lane. The real divergence was discarded as an echo, nothing
re-queues it, and `Skipped: Recent Self-Write` is a terminal node.

Then the Watchdog latched `override_main_level` 48 seconds later, which excluded main level from
all corrective action and froze the split until the override cleared.

The gate needs to be field-scoped — separate `last_write_at` for the mode channel and the
fan/tilt channel — and stamped at the service call, not at release.

### P1-2. Nothing is retained, so none of this is diagnosable

All four workflows set `saveDataSuccessExecution: "none"`. Every silent-drop path ends in
*success*: the echo skip, `Valid Event?` false, the token-verify false branches, both `noop`
paths, and Apply's unconfirmed-but-expired path. The Controller has no retained execution newer
than yesterday despite confirmed writes today. Two agents independently said this is the single
biggest obstacle to diagnosing the system.

Suggested: enable success retention on Controller and Apply, which are event-driven. Leave the
Watchdog off — it runs 1,440 times a day.

### P1-3. The forwarder watches mode on only two of seven heads

`automation.hvac_n8n_sequencer_forwarder`: the `main_head_state` and `main_head_temp` triggers
list only the living room and dining heads. The other five appear only under the `recovered`
trigger. A mode or setpoint change on Anthony, Autumn, either master or the basement — from the
app, the car or the IR remote — is never forwarded. n8n learns about it only via the Watchdog's
60-second poll, whose only response is to latch an override.

For five of seven heads, the app bypasses the entire control plane.

### P1-4. The run mutex is released before the writes it guards have happened

All eight `Dispatch Zone - *` nodes are `waitForSubWorkflow: false`, so `Release Run Mutex` fires
while the Zone Runners are still calling Apply. A second event then acquires the mutex, reads
pre-write state, and recomputes the same actions. The `turn_on → mode → temp` ordering guarantee
holds within a runner but breaks across two racing runners, and on these heads a mode change
reloads that mode's remembered setpoint — so the temperature just written gets clobbered.

Corroboration: `Renew Run Mutex` in Apply filters on `owner = mutex_token`, which the controller
has already blanked. That node is dead code, and only makes sense under `waitForSubWorkflow: true`.

### P1-5. A write that never took effect is recorded as success

`HVAC Apply`, two compounding defects:

- `Evaluate Confirmation`'s `satisfied()` helper ends `return true`, while the otherwise identical
  helper in `Decide If Write Needed` ends `return false`. Any action with a missing or misspelled
  `verify_type` is sent and then declared confirmed without checking anything.
- `Confirmed Or Timed Out?` tests only `done = ok || expired`. Confirmed and timed-out take the
  same branch. The `confirmed` flag is computed and never read again.

A head that accepted the call but never changed is indistinguishable from one that obeyed. There
is no Telegram on an unconfirmed write.

### P1-6. Two authenticated API writers are reverting each other

The HA agent found user `ac4b1a79…` and user `b66b7657…` both writing `climate.*` and
`input_select.water_heater_mode`, undoing each other. `b66b7657…` appears in your dashboard config
as a user-visibility filter, so it is your own account — which is what the app's long-lived token
authenticates as. That points at app-versus-n8n, and is consistent with P1-3: the app writes heads
directly and n8n never hears about it.

Worth confirming which token is which before changing anything.

## P2 — The system states things that are not true

- **The OTA installer installs nothing.** `installApk` never reads `apkPath`. It plays seven
  scripted progress messages, then writes `installed_version_override` and reports the new version.
  No `PackageInstaller`, no intent. The panel permanently reports a build it is not running, so any
  future "which version is this tablet on" answer is fabricated. `HvacViewModel.kt:2086-2125`
- **The pool view invents readings and its entire history graph.** Missing sensors fall back to
  79.0 °F, pH 7.35, ORP 561, rendered identically to live values. The history chart is
  `Math.cos()` plus random noise, under a comment claiming it is anchored to live metrics.
  `PoolDashboardView.kt:141-143, 145-248`
- **The car reports a full hot-water tank and a healthy pool when the sensors are missing** —
  `?: 100.0` and `?: "Normal"`. Both fail toward reassurance.
- **The who's-home popup claims "No change in recorded history" when the history call failed.**
  `fetchPresenceSince` returns an empty map on any exception, and the UI cannot tell that apart
  from a genuine empty result. Two code comments describe a `last_changed` fallback that the code
  does not have. `HomeStatus.kt:355-361`
- **Optimistic UI never reverts.** Both `setZoneHvacMode` and `setTargetTemperature` write to
  `_uiState` before the call; on failure only a transient toast is set. Correction depends on a
  WebSocket push, which is exactly what is missing when the write failed. The panel can sit
  showing HEAT while the house is OFF.
- **The notification's "Outside Temp" is the forecast high**, not the outdoor reading, and it
  overwrites the cached real value every 60 seconds.
- **Six dead solar entity IDs** in both copies of `layout_config.json`. No `solcast` or
  `panel_usage` entity exists in HA at all, so those tiles render "--" permanently.

## P2 — Safety by design

- ~~**Whole-house OFF is one tap from the lock screen.**~~ and ~~**The panel confirms a comfort
  change but not turning the heat off.**~~ **Decided 2026-09-20: leave both unconfirmed.** The
  heat-to-cool prompt exists to protect the compressor from a reversed cycle; off carries no
  equivalent risk, and it is a routine action that should not nag. The asymmetry is intentional.
  Do not re-raise. See the Decided section of the logic traces.
- **`zone_enable_basement` is off right now**, which makes the basement invisible to the
  controller, the watchdog and the bot's verification count — it reports "confirmed on N of N"
  while omitting it. There is no "this zone has been unmanaged for N days" alert anywhere.
- **Night→Day hinges on one phone's charging cable.** `automation.morning_work_wakeup` triggers on
  `sensor.z_fold_7_battery_state_2` going to `discharging`, gated on battery above 80%. If the
  phone stays plugged in, is below 80%, or is replaced, the house never leaves Night setpoints —
  and every latched override stays latched, because a schedule change is the release path.

## P3 — Nuisance and polish

n8n: `Notify Mutex Timeout` says 200s where the code sets 600s. `input_select` feedback writes are
never echo-suppressed, so a fan/tilt UI write burns a full controller run. `Notify Controller
Error` is unthrottled, unlike its two siblings. Zone Runner continues after a failed `turn_on`, so
mode and temperature are still sent to a head that is still off. `dry` mode reads the *heating*
setpoint in both the controller and the watchdog — they agree with each other, so nothing fights.
The `airstage_write` global lock is now nearly vestigial. `home_mutex` is missing from the
Watchdog's lock filter, the same class of bug as a past regression.

App: a stale door alert outranks the offline banner, so a cached "GARAGE SOUTH OPEN" shows at full
confidence while disconnected. The alert strip's exit animation never renders. `clearFeedback()` is
called in exactly one place, so a quick-action message can sit on the wall indefinitely. The zone
popup runs an infinite animation even when idle. Version ties favour the stored config, narrowing
OTA recovery. `QuickActionConfig.confirm` is defined and read nowhere, so the car opens a garage
door on a single tap. "Whichever zone started first" is documented in two places and implemented in
neither — both just take list order. The cool floor is 64.0 in the app and 64.5 in n8n.

Naming: one room is "Master 1" on the panel, `bedroom_1` in config and n8n, "Bedroom 1" in Watchdog
Telegram messages, "HP Bedroom" when the Watchdog uses the HA friendly name, and "Gym" in the
notification. `climate.hp_dining_room` has no card and no helpers, so the panel cannot see or
control one of the seven heads — and the Watchdog will Telegram you about a room that does not
exist in the app.

Build: the public release workflow runs `assembleDebug` and attaches a debuggable APK.
`isMinifyEnabled = false`. CI falls back to `.env.example`, which holds only placeholders, so the
CI-built APK carries no real secrets — locally built ones do.

## Refuted — do not chase these

- **My 12:33 forwarder-miss claim.** No state change occurred at 12:33; the forwarder fired within
  ~2s of every real transition.
- **A second competing controller in HA.** I checked: `gemini_hvac_master_sequencer_6`,
  `gemini_hvac_expected_vs_actual_watchdog_2`, `hvac_engine_override_recovery_11` and
  `gemini_hvac_main_level_bi_directional_sync` are all **off**. Only three forwarders are enabled.
- **Missing lock rows or missing entities.** All 9 lock rows, all 7 heads, all 60 zone helpers, all
  4 rest_commands and every entity in `layout_config.json` resolve live. Both copies of the config
  are byte-identical.
- **Case mismatch on `house_schedule_state` in n8n** — both consumers lowercase before use.
- **The `'Quiet'` fan special case and the swing-mode enum** — both correct as written.
- **Mirror infinite loop** — it converges by state equality.
- **Run-mutex leak on error paths** — every acquiring path reaches the release.
- **`Check Recent Self-Write` emitting zero items** — it has `alwaysOutputData: true`.
- **Stuck locks** — all TTL-bounded, and all 10 rows currently show `expires_at = 0`. The thing
  that actually gets stuck is `input_boolean.override_<zone>`, which has no timer at all.
