# Session notes — 2026-11-21: releases move to app-builder

Follows `HANDOVER-2026-11-06.md`. App **82.0**, layout config unchanged at **6.34.0**; then
app **83.0**, config **6.35.0** for the sign-in change at the end.

## What changed

APK installs and updates now come through Obtainium from the releases of `cstone1983/app-builder`,
titled `hvac <version>`. That repo checks out `main` here, builds `:app:assembleRelease` unsigned,
sets versionCode = 1000 + its run number and versionName = `<versionName>.<run>`, signs with one
shared release key and publishes a pre-release. Promoting it to a full release deploys it.

The devices have to be reinstalled once onto that key (uninstall, then install through Obtainium).
After that, updates install in place.

## What was checked

- **`release` against `panel`,** both built on the PC from the same `.env`. The manifests are
  identical, and 175 of the 177 files in the APK have the same checksum. The two that differ are
  `classes2.dex`, where the only difference in the disassembly is `BuildConfig.BUILD_TYPE`
  ("panel" / "release"), and the baseline profile derived from it. Neither build is debuggable; R8
  is off in both. So the release is the same app as panel, signed with a different key.
- **A clean clone with no `.env`, no `local.properties` and no keystore** builds with app-builder's
  own init script. The APK comes out unsigned with the version numbers app-builder sets, and
  `BuildConfig.VERSION_NAME` follows them, so Settings shows e.g. "v82.0.57".
- **The in-app layout update** never reads a GitHub release.

## What an app-builder release does not have

A build on the development PC reads `.env`. app-builder has none, so its release gets the
`.env.example` placeholders:

| Value | PC build (`panel`) | app-builder release |
|---|---|---|
| Home Assistant token | built in | none |
| Main (remote) Home Assistant address | built in | none |
| Home (LAN) address | built in | built in (it is in `.env.example`) |
| GitHub token | built in | none |

These cannot be made the same: the repo and the releases are public. Three fixes went in so the
app works without them (82.0):

1. **Sign-in screen on a fresh install.** Start-up used to mark the app signed in whatever it had,
   so a build with no token opened an empty dashboard with no way in. It now shows the sign-in
   screen when there is no token (`resolveHaStartup`, `api/BuildDefaults.kt`).
2. **Sign-in through the home address.** With no main address, LOG IN checks the token against the
   home address (`signInUrl`) and saves that as the main address. Enough for the wall tablets. The
   phone needs the real main address: CHANGE SERVER ADDRESS on the sign-in screen, or Settings >
   Connection afterwards.
3. **Layout checks without a GitHub token.** GitHub allows 60 unauthenticated API requests an hour
   per IP address. Three devices at two requests every five minutes would use 72, and Obtainium
   draws on the same allowance. The background check now reads the layout file from the branch
   first and only asks the API when it has changed (`layoutApiCheckNeeded`).

## Later the same day: username and password sign-in (83.0, config 6.35.0)

Typing a long-lived token on a wall tablet is not practical, so the sign-in screen now takes a
username and password and has Home Assistant make the token. See "Sign-in (83.0)" in
`SYSTEM-REFERENCE.md` section 6.8 for the requests.

- **What was wrong with the old code.** `startLoginFlow` / `submitLoginStep` / `getAccessToken`
  (never called) sent the handler `["homeassistant", "default"]` (Home Assistant: 404 "Invalid
  handler specified"), left `client_id` out of the second request (400), used
  `http://localhost/` as the client id, and parsed answers into a model that required `step_id`,
  which a successful login does not have. They are removed.
- **Checked against** Home Assistant's source on the `dev` branch (`components/auth/login_flow.py`,
  `components/auth/__init__.py`, `auth/providers/__init__.py`, `components/http/ban.py`) and
  `docs/auth_api.md`, with the house on 2026.11.2. `/auth/revoke` is the current revoke endpoint;
  `action=revoke` on `/auth/token` is deprecated but still handled, and is what the app sends.
- **Tests.** 65 new unit tests (228 in all): 42 on parsing, the next-step decision and the error
  wording; 16 that run the client against a fake Home Assistant (MockWebServer, a test-only
  dependency) and check every request body, that nothing is sent twice, and that no request
  carries a token header; 7 that draw the screen at the kitchen tablet's size and check what its
  buttons send. `gradlew recordRoborazziDebug --tests com.example.SignInScreenTest` writes
  pictures of the screen to `app/src/test/screenshots/sign_in_*.png` (gitignored).
- **The screen.** `ui/SignInScreen.kt` replaces the login screen that was in `HvacDashboard.kt`.
  On a wide screen the fields sit in pairs with LOG IN beside the device name, so the button is
  on screen without scrolling on a tablet lying on its side, and an error shows above the fields.
- **Old tokens are not removed.** Each sign-in adds a token to the account. CLEAR SESSIONS /
  TOKENS on the sign-in screen only forgets the device's own copy; its revoke request sends the
  long-lived access token, which Home Assistant does not treat as a refresh token. Delete stale
  entries in Home Assistant under Profile > Security.
- **Not tested against the real server.** That needs a real username and password typed on a
  device. The development PC cannot reach the server's LAN address either, so not even the first
  request was tried for real. The first real sign-in is the test: do it on one tablet.
